  1. 프론트엔드와 클라이언트가 항상 같은 개념이 아닌 이유는?

    풀이 보기

    프론트엔드 · 백엔드는 무엇을 맡는가(기능 분담)의 구분이고, 클라이언트 · 서버는 누가 요청하고 누가 응답하는가(관계)의 구분이기 때문이다. 예제 앱에서 원격 법령 서버에 묻는 백엔드 코드(core/mcp_client.py)는 그 순간 클라이언트이면서 여전히 백엔드다.

    다시 보기: 움직이는 그림 7-A 두 가지 질문, 두 가지 분류

  2. 카드가 보였는데 새로고침하니 목록이 비었다. 네 단계 점검 순서는?

    풀이 보기

    ① 화면: 버튼 클릭이 처리되고 다시 불러오기가 일어나는지 → ② 요청: 개발자 도구 Network 탭에 목록 요청이 나가는지 → ③ 서버: 응답 코드와 서버 로그, 응답 내용 → ④ 저장소: 데이터가 실제로 기록돼 있는지(새로고침 뒤 다시 조회). 화면에서 저장소 쪽으로 차례로 내려가며 어디까지 정상인지 찾는다.

    다시 보기: 움직이는 그림 7-B 데이터는 저장소까지 도착해야 한다

  3. 마지막 한 자리를 두 사람이 동시에 신청했다. 각자 화면에서 계산해 확정하면?

    풀이 보기

    두 화면 모두 상대의 최신 신청을 모른 채 ‘남은 자리 1’을 보고 성공이라고 판단할 수 있다. 그러면 한 자리에 두 사람이 확정된다. 남은 자리는 공유 저장소를 가진 서버가 한 번에 하나씩 확정해야 하고, 화면은 그 결과를 보여 준다. 마지막 판정은 서버가 한다.

    다시 보기: 움직이는 그림 7-C 고칠 곳은 어느 쪽인가

  4. 화면은 /register에 name을, 서버는 /watch에서 law_name을 받는다. 어떻게 맞출까?

    풀이 보기

    설계 문서(docs/PLAN.md · SPEC.md)와 서버가 /watch · law_name을 쓰므로, 화면 쪽 tracker/page.tsx의 등록 요청을 /api/tracker/watch와 law_name으로 고친다. 목록을 받는 쪽의 name · last_checked도 서버의 law_name · last_checked_at에 맞춘다. 한쪽만 고치지 말고 양쪽을 함께 보고, 고친 뒤 실제 응답으로 등록과 목록 표시를 확인한다.

    다시 보기: 움직이는 그림 7-D 이름이 어긋난 계약

  5. 감시를 등록했는데 서버를 다시 켜니 목록이 비었다. 이유와 필요한 것은?

    풀이 보기

    reg_tracker/service.py가 감시 목록을 데이터베이스가 아니라 서버의 메모리(self._watched)에 담기 때문이다. 서버가 다시 켜지면 메모리가 비어 목록도 사라진다. 서버를 다시 켜도 남게 하려면 백엔드 처리 코드가 데이터베이스 표(core/database.py에 정의만 된 watched_laws)에 기록하고 읽도록 바꿔야 한다. 누구의 목록인지 구분하려면 사용자 확인도 필요하다.

    다시 보기: 움직이는 그림 7-B 데이터는 저장소까지 도착해야 한다

정확성 메모 — 카드의 분류는 예제 앱(smart-korean-legal-platform) 코드 기준이고, 결과 미리보기의 법령 이름은 설명용 예시입니다. /register 요청이 거절되는 정확한 상태 숫자는 실행 환경에 따라 다를 수 있어 ‘거절’로만 적었습니다.
